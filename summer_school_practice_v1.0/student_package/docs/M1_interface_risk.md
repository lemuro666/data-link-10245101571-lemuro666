# M1 接口、通信与风险说明

## 1. 原始接口提供什么数据？

OpenSky 匿名 REST API 返回一个顶层对象，包含批次时间 `time` 与状态向量数组 `states`；每个状态向量仍是按固定索引排列的数组，包含目标标识 `icao24`、呼号、来源国家、位置时间、最近联系时间、经纬度、气压/几何高度、地面状态、地速、航向、垂直速度等字段。本实践使用离线快照 `raw_states.json`，不访问实时 API。

## 2. 为什么原始数据不是完整态势结果？

- 状态向量是“按索引排列的原始数组”，不是按目标组织的当前态势表，同一目标可能有多条历史记录。
- 时间、高度存在“优先字段 + 回退字段”的关系，缺失值需要用 `null` 表达，不能用 0 代替。
- 数据没有经过帧校验、关联去重、语义映射和质量检查，不能直接回答“每个目标当前是什么状态、数据是否可信”。

## 3. 为什么发送方需要把内部状态封装成消息？

- 内部结构化记录（字符串、浮点数、布尔值）不能在链路上直接传输，需要转换成双方共同约定的字节序列。
- 必须固定字节序（大端）、位宽、比例因子、偏置、有效性标志和保留位，否则接收方无法无歧义地恢复数值。
- 通过定点量化压缩浮点数，用 `validity_flags` 区分“真实零值”和“字段缺失”。

## 4. 为什么接收方要检查长度、类型、校验和与保留位？

- 长度：确保一帧承载一条完整消息，识别不完整尾帧。
- 类型（magic/version/message_type）：确认是本协议、本版本、本消息类型。
- 校验和：检测传输中的比特错误。
- 保留位与标志一致性：确保发送方按规范置位，避免把非法/越界数据误当有效数据。
- 这些检查共同构成 `message_valid` 的判据；`message_valid` 只代表格式校验通过，不代表来源真实性或安全完整性。

## 5. CSV 与 SQLite 分别承担什么角色？

- CSV：无依赖、可人工检查、便于提交审阅，承担必做结果输出。
- SQLite：支持结构化查询、事务与 NULL 语义，作为 M3 选做路径。
- SQLite 不是必做前置条件；不可用时继续使用 CSV 完成必做任务。

## 6. 至少三个工程风险及处理

1. **字段缺失**：位置、时间或呼号缺失会导致态势不完整。处理：用 `null` 表达缺失，`validity_flags` 逐字段标记有效性，缺失可选字段不使整帧无效，但业务层标记 `position_valid=false` 并产生 `POSITION_MISSING` 告警。
2. **消息损坏**：传输中比特翻转会被校验和/保留位检查发现。处理：非法帧记录到 `validation_log.csv` 并把 `message_valid` 置为 false，不参与航迹与态势，且不导致程序崩溃。
3. **量化误差**：经纬度 22 位定点量化会引入不超过一个量化单位的误差。处理：编码前量程检查，往返误差与容差比对，禁止静默截断/取模。
4. **接口延迟**：时间戳落后于批次时间。处理：用 `time_source` 区分 `position_time` 与 `last_contact_fallback`，超过阈值产生 `DATA_DELAYED` 告警。
5. **存储失败**：输出目录不可写或 SQLite 不可用。处理：环境检查提前验证目录读写，SQLite 不可用时降级为 CSV。
